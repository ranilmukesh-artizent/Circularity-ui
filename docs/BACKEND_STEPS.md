# Backend: step-by-step build

**For:** the engineers building the backend of the full-stack POC.
**Plan and decisions:** [PLAN_FULLSTACK_POC.md](PLAN_FULLSTACK_POC.md) (D1: only SAP S/4HANA and SAP Ariba are mocked as SAP; every other source keeps its vendor as a generic mock).
**Branch:** `feature/fullstack-poc`. **Run it:** [apps/README.md](../apps/README.md).

## Where we start

| Part | State |
|---|---|
| Frontend (`apps/web`) | Every screen ported to React. It talks to an **in-browser mock backend**: the demo's own script, behind the typed facade in `apps/web/src/api/`. Every change goes through `invoke(actionId, input)` |
| `di-api` / `di-worker` (`apps/api`) | Skeleton: health checks, Alembic, Postgres job queue with retries, tests |
| `source-sim` (`apps/source-sim`) | Registry of the 21 systems, one empty Postgres schema each |
| Stack | Docker Compose: Postgres (`di`, `sources`), source-sim, api, worker, web. Runs in WSL |

## How the steps fit together

```
B1 golden data ─┬─▶ B2–B5 source-sim (mock systems, filled by the seed)
                │
                └─▶ B6–B8 di foundations ─▶ B9 connectors and sync ─▶ B10–B12 decision core and actions
                                                                            │
                                         B13 outbound and reconcile ◀───────┘
                                                    │
                     B14 read APIs ─▶ B15 live updates ─▶ B16 MCP ─▶ B17 frontend switch-over ─▶ B18 hardening
```

**The one rule:** the `di` database is filled only through the connectors, over HTTP, from source-sim. Nothing seeds `di` directly.

**How we know it is right:** the demo is the specification. Its script runs headless in Node (the React app already does this), so **B1** dumps its numbers as golden files. Every later step has a parity test against those files. A step is done only when its parity test passes.

**Each step:** one pull request; tests and lint green (`pytest`, `ruff`); the stack still starts with `docker compose up`; the "Done when" line is true.

## B1. Golden data from the demo

**Goal:** a frozen, machine-readable copy of what the demo computes, to test the Python backend against.

1. `apps/web/scripts/dump-golden.mjs`: run the engine headless (as `engine.ts` does) and write JSON to `fixtures/golden/`:
   - `world.json`: tenants, sites, facilities, classes, routes, gates, model versions, `AS_OF`.
   - `cases.json`: the 128 live cases with evidence, routes (terms, gates, P10/P50/P90, rank), recommendation, stage, execution detail.
   - `decisions.json`: the ~1,400 closed decisions (`ROWS`).
   - `sources.json`, `canonical.json`, `mappings.json`, `events.json`, `conflicts.json`, `tools.json`, `agents.json`.
   - `policy.json`: `ROLE_POLICY`, `ACCOUNTS`, `PERM_ACTS`, `RB_SECS`.
   - `figures.json`: headline numbers per role (Command Center key figures, Analytics totals, nav badges) and the result of the demo's `runInvariants()`.
   - `actions.json`: for a scripted RT-1048 journey (submit → approve → acknowledge → outcome → confirm), the output of each `invoke()` call.
2. A README in `fixtures/golden/` that says how to regenerate the files and when (only when `index.html` changes on purpose).

**Done when:** `node apps/web/scripts/dump-golden.mjs` writes every file, the demo's invariants all pass, and the output is identical on two runs (the seed is deterministic).

## B2. Seed model in Python

**Goal:** source-sim holds the same synthetic world as the demo, as typed Python objects, ready for the mock systems to load.

**Decision (19 Nov 2026):** the seed is **loaded from the B1 golden files**, not re-generated by a Python port of the demo's generator (~120 KB of JavaScript). The golden files are the generator's exact output, so the seed matches the demo by construction and there is no second copy of the generation code to keep in step. To change the synthetic world, change `index.html` and regenerate the golden files. A Python generator can still be written later if the world must grow beyond the demo (more cases, other customers).

1. `apps/source-sim/sim/seed/`: read `fixtures/golden/*.json` (mounted into the container), resolve the `$ref` back-references, and validate everything into typed models (pydantic):
   - the world: tenants, sites, facilities, asset classes, routes, gates, model versions
   - each case's source facts: asset, owner, location, condition, spec, demand, evidence, and the cost and value lines per route
   - the closed decisions
   - the source catalogue
2. Keep **source facts** apart from the **demo's computed results** (gates, ranges, rank, recommendation) and **workflow state** (stage, approval, execution). The mocks seed only facts; the decision engine (B10) recomputes the results and is tested against the golden values.
3. Parity tests:
   - all 128 cases and 1,400 decisions load
   - every route's net equals the sum of its cost and value lines
   - RT-1048's values match the demo
   - the sources match `sim/registry.py`

**Done when:** the parity tests pass inside the source-sim container.

## B3. SAP S/4HANA mock

**Goal:** an S/4HANA-shaped system on Postgres that answers like the real OData services.

1. **Tables** (schema `s4`, SAP names and key columns): `MARA`, `MAKT`, `MARC`, `MARD`, `MBEW`, `EKKO`, `EKPO`, `RKPF`, `RESB`, `MKPF`, `MSEG`, `ACDOCA`, `T001W`, each with `LastChangeDateTime`. Created by source-sim's own migrations.
2. **Seed loader:** write the B2 world into these tables as S/4 would hold it (materials per asset class, stock per plant, purchase baseline per demand, plant codes per site, e.g. `1030` → Site 3).
3. **OData v2 read services** under `/sap/opu/odata/sap/`: `API_PRODUCT_SRV/A_Product`, `API_MATERIAL_STOCK_SRV/A_MatlStkInAcctMod`, `API_PURCHASEORDER_PROCESS_SRV/A_PurchaseOrder` (+ `to_PurchaseOrderItem`).
   - Query options: `$filter` (eq, ne, gt, ge, lt, le, and, or, `substringof`), `$select`, `$top`, `$skip`, `$orderby`, `$expand`, `$inlinecount=allpages`, `$format=json`.
   - Response shape `{"d":{"results":[…],"__count":"…"}}`, with `__metadata`.
   - Delta: `$filter=LastChangeDateTime gt datetimeoffset'…'`.
   - A minimal `$metadata` document per service.
4. **Auth:** Basic auth, and an OAuth 2.0 client-credentials token endpoint. Users and clients come from config.
5. **Writes:** `GET` with `x-csrf-token: Fetch` returns a token and cookie; a `POST` without a valid token returns 403. Write services: `API_RESERVATION_DOCUMENT_SRV/A_ReservationDocumentHeader`, `API_MATERIAL_DOCUMENT_SRV/A_MaterialDocumentHeader`. They create rows and return SAP document numbers.
6. **Errors:** the SAP error body `{"error":{"code":"…","message":{"lang":"en","value":"…"}}}`, with the right status codes.

**Done when:** contract tests call each service the way a real S/4 client would (CSRF fetch, then post, then read back), and the values read back match the golden data.

**Status: done (19 Nov 2026).** Code in `apps/source-sim/sim/s4/` (tables, seed, services, security, API) and `sim/odata/` (a generic OData v2 layer that B5 can reuse). 43 source-sim tests pass. How the seed maps into S/4 is described in `sim/s4/seed.py`.

Known limits, each picked up by a later step:
- **Journal entries:** `ACDOCA` exists, but there is no journal-entry read service yet. It arrives in B13 with the cost postings.
- **Clock:** writes stamp wall-clock time until B6 adds the simulated clock.
- **Events:** events are written to `sim.outbox`, but nothing delivers them until B6.
- **Formats and batching:** JSON only, with no `$batch`.

## B5c. AWS IoT Core mock

**Decision (20 Nov 2026):** AWS IoT Core (`iot`, the demo's device telemetry) gets a full vendor mock, to the B5b standard. di still starts with it **not provisioned**, as in the demo, so the starting state and the parity tests do not change. It is a synthetic mock; no real AWS account is involved.

**Status: done (20 Nov 2026).** Code in `apps/source-sim/sim/vendors/aws_iot/` (the docstring lists the documentation followed and every assumption). The adapter is `apps/api/di/connectors/adapters/aws_iot.py`.

**What is mocked:**
- **Control plane** (`/aws-iot/iot`): ListThings, DescribeThing, ListThingGroups, DescribeThingGroup, ListThingsInThingGroup, ListJobs, DescribeJob, ListTopicRules, GetTopicRule. Paging uses `maxResults` and `nextToken`.
- **Data plane** (`/aws-iot/data`): Get, Update and DeleteThingShadow, classic and named. Shadows have desired, reported and delta state, metadata, version and timestamp. Also ListNamedShadowsForThing, Publish, ListRetainedMessages and GetRetainedMessage.
- **The fleet:** 77 condition-monitoring kits.
  - One kit per returned motor or pump of the live cases. These are offline and hold their last report. The thing attribute `assetTag` links each kit to the asset, for example `cm-mtr-2041` → MTR-2041 for RT-1048.
  - 24 kits on redeployed or re-leased assets in service. These are online.
  - The named shadow `condition` holds operating hours, duty cycle %, vibration in mm/s RMS with its ISO 10816-3 zone, bearing °C, and the last alarms. The kits publish on `dt/<fleet>/<thing>/telemetry` and `/events`.
  - Two firmware jobs.
- **Seed values:** RT-1048 shows 18,450 h, 96.4 % duty (24/7), 2.8 mm/s and 66 °C.
  - Hour counters agree with Maximo's RUNHOURS meter, except for one case in eight, where Maximo's reading is older.
- **Simulated clock:** every simulated hour the online kits report. Each report adds hours, takes a sample, raises an alarm when vibration reaches 7.1 mm/s or the bearing reaches 90 °C, and updates the shadow.
- **Rules:** three topic rules deliver to the HTTPS destination. That destination is the shared outbox: CloudEvents `aws.iot.rule.<rule>`, signed with HMAC. The pull path for backfill is ListRetainedMessages plus GetThingShadow.
  - The rules start **disabled** (not provisioned), so no telemetry fills the shared outbox before anyone connects (it had pushed RT-1048's own events out of the milestone test's view). EnableTopicRule and DisableTopicRule (`POST /iot/rules/{name}/enable|disable`) switch them; di's connect enables them and its disconnect disables them.
- **Auth:** SigV4, checked against two demo IAM users: the connector, and a read-only viewer. Errors are AWS JSON: `x-amzn-ErrorType` and `{"message"}`. Refusals are MissingAuthenticationToken, UnrecognizedClient, InvalidSignature (including 15-minute clock skew), Unauthorized (401), ResourceNotFound, InvalidRequest and Conflict.
- **Faults:** the shared fault injection answers in AWS's shape. 429 gives ThrottlingException, 5xx gives InternalFailure, `unavailable` gives ServiceUnavailable, and `token_expired` gives ExpiredToken (403). `faults.SHAPES` lets any mock do the same.

**The adapter:**
- **Full sync:** ListRetainedMessages, then ListThings, then GetThingShadow `?name=condition` per thing.
- **Delta sync:** only the things whose retained telemetry or events changed after the cursor.
- **Retries:** throttling is retried with backoff.
- **Facts:** `asset.run_hours`, `asset.iot_thing`, `asset.source_refs`, and `condition.duty_cycle_pct`, `vibration_mm_s`, `vibration_zone`, `bearing_temp_c`, `telemetry_events` and `telemetry_at`.
- **Authority:** iot has authority over Operating hours (`asset.run_hours`) and Duty (`condition.duty_cycle_pct`). Where Maximo's meter disagrees, a conflict opens naming iot.
- **Webhooks:** rule deliveries reach the shared webhook receiver, which queues a delta sync while iot is connected and ignores them otherwise.

**How to switch it on:**
- At run time, as Admin or Developer, call `POST /api/sources/iot/connect`. The source goes live, its topic rules are enabled, and a full initial sync is queued.
- To switch it off, call `POST /api/sources/iot/disconnect`. With `?purge=true`, everything it synced is removed as well.
- To start connected by default, set `DI_IOT_CONNECTED=true` for the api and worker, or set `iot_connected: bool = True` in `apps/api/di/config.py` (one line).
- While iot is not provisioned, `source.sync` for iot still answers "No connector for iot.", as before.

**Tests:** source-sim has 11 contract tests (`tests/test_aws_iot.py`). The api has 8 adapter tests (`tests/test_adapter_aws_iot.py`); they connect iot and put the starting state back afterwards.

**Left out:**
- certificates and policies, Fleet Indexing, Device Defender
- job executions and CreateJob
- creating things, groups or rules
- MQTT connections (devices are simulated server-side)
- rule SQL beyond the seeded forms
- real service rate limits (throttling comes only from fault injection)

The frontend still shows the demo's "Not provisioned" version text, which comes from `sources.json`.

## B6. Events, faults and the simulated clock

1. **Outbox:** every write in source-sim writes an outbox row. A sender pushes it as a CloudEvents webhook to subscribed URLs (S/4 event names such as `sap.s4.beh.reservation.v1.Reservation.Created.v1`; vendor-style names for the generic mocks). Delivery is retried until acknowledged.
2. **Simulated clock:** `/_sim/clock` starts at the demo's `AS_OF` (7 Oct 2026 09:00) and can advance. Work orders, shipments and repairs complete on that clock and emit their events.
3. **Fault injection:** `/_sim/faults` can add latency, return 5xx, expire a token or make a feed stale, per system. The seed starts Ritchie Bros. with an expired token, as in the demo.
4. **Reset:** `/_sim/reset` rebuilds every schema from the seed.

**Done when:** a test advances the clock, receives the completion webhooks in order, and a fault makes the next call fail as configured.

**Status: done (19 Nov 2026).** The building blocks, each a module in `apps/source-sim/sim/`:
- `clock.py`: simulated time, stored in Postgres
- `scheduler.py`: named handlers that run when the clock reaches their time
- `webhooks.py`: signed CloudEvents with retry and backoff
- `faults.py`: one middleware, so every mock gets latency, error, unavailable and token-expired faults
- `admin.py`: the `/_sim/*` control endpoints, plus a webhook sink for demos

S/4, Ariba and the generic mocks stamp their changes with simulated time. Nine tests cover it.

The demo's starting fault (Ritchie Bros. token expired) is applied by `POST /_sim/faults/demo`, or at start-up with `SIM_DEMO_FAULTS=true`. It stays off by default so contract tests see healthy systems.

Mocks schedule their own completions as they get their write paths. For example, a Maximo work order completes in N days. That wiring happens in B13, where the instructions arrive.

## B8. Action endpoint (the contract the frontend already uses)

**Goal:** `POST /api/actions/{id}` behaves exactly like the demo's `invoke(id, input)`.

1. **Registry:** in `di/actions/`, one module per area, each action declaring `id`, `risk` (read, draft, act, commit, system), `perm`, `scope`, input schema and handler. The ids are the 76 from the demo (list them with `actionCatalog()` in the frontend).
2. **The pipeline, in the demo's order:**
   1. Validate the input.
   2. Check that someone is signed in.
   3. Reject `system`-only actions from people.
   4. Check the permission.
   5. Check case scope (tenant and warehouse).
   6. Apply the agent gate.
   7. Apply the action's own guard.
   8. Apply policy limits.
   9. Check idempotency.
   10. Run the handler.
   11. Write to the journal.
   12. Emit an event.
3. **Response shape:** `{ok:true, output, key, action, seq}` or `{ok:false, error:{code, message}}`, with the demo's error codes (`validation_error`, `out_of_scope`, `tenant_boundary`, `approval_required`, `limit_exceeded`, `not_found`, `conflict`, `duplicate`).
4. **Undo and reset:** undo marks journal entries as undone and rebuilds the affected state. Reset for a case or for everything is admin and demo only.
