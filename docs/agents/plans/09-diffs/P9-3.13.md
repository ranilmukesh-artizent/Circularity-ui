# P9-3.13: tool-fleet numbers before and after (the live queue plan)

R8. An org's open tool returns are planned together (`di.services.cases.tool_queue`, the planner of I-5, no language model):
a named order is filled once, refurbishment stays within the repair center's slots (the pack's `slots`, less the refurbishments
in progress), and a return that arrives plans the others again (`case.replan`). The case's own decision is the same plan.
`GET /api/screens/toolfleet/{id}` now serves `plan`: `holds`, `headline`, `contested`, `kinds`, `lost`, and the plan's `total`,
`fcfs` (first come, first served), `gain` and the slots.

## The sample world and the industrial demo: no change

The planner, its inputs and the valuer are unchanged (`HeuristicPlanner` is `plan_queue`): the prototype's 26 open returns keep
every best path and net (`test_valuer_tool_fleet.py`, `test_po_golden.py`), and the 128 cases and RT-1048 do not move
(`test_screens_case.py`, `test_queue_planner.py`).

## Cases opened from data

No number changes. `tool_queue.open_queue` and `plan_of` read the queue the decision already used (`intake.tool_queue`, now
built by `intake.queue_of`); `replan` runs `replan.on_opened` as the `case.replan` job did. What is new is the read: the order a
return takes, the reason a return lost one ("FC-30117-R (Brightline Mechanical) is planned for RT-1102, where it adds more
across the queue") and the gain over first come, first served.
## Equal returns: ties go to the lower case number

The queue was read with the case being decided last, so of two returns that value the same (two grade A returns that both want one renewal) each saw itself last and lost: neither took the order. `intake.tool_queue` now reads the queue in case id order, as `tool_queue.open_queue` does, so the lower case number takes it and the other reads why. Only ties change; a queue with no tie decides as before (`test_queue_planner.py`, `test_tf_intake.py`, `test_tf_life.py`, `test_tf_paths.py`, `test_valuer_tool_fleet.py` and the PO goldens pass).
